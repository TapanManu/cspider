## ADDED Requirements

### Requirement: Field and enum-constant resolution
The system SHALL resolve references to change units of kind FIELD and ENUM_CONSTANT using
position-anchored reference queries, in the same manner as methods and constructors.

#### Scenario: Field with readers
- **WHEN** a changed field is read in three methods across two files
- **THEN** the system resolves three reference sites, each carrying its file and line as evidence

#### Scenario: Enum constant
- **WHEN** an enum constant is added to an enum that a switch statement covers
- **THEN** the constant's references resolve like a field's, and the switch site appears among them

### Requirement: Unresolved variables are declared UNKNOWN
The system SHALL mark every unresolved change unit of kind FIELD or ENUM_CONSTANT as UNKNOWN with a
stated reason, and SHALL NOT report it as having zero usages — whether it went unresolved because
resolution was unavailable, because a bound was reached, or because no base image exists for a removed
field.

#### Scenario: Resolution unavailable
- **WHEN** the analysis runs without resolution enabled and a field has changed
- **THEN** the field is reported UNKNOWN with the reason that it was not resolved, rather than showing no usages

#### Scenario: Removed field without a base image
- **WHEN** a field is REMOVED and no base-image index is available
- **THEN** its usages are reported UNKNOWN with that reason, and never as zero or SAFE

#### Scenario: Beyond the symbol budget
- **WHEN** a changed field falls outside the per-run symbol budget
- **THEN** it is marked UNKNOWN naming the budget as the reason, and the run reports how many fields were omitted

### Requirement: Removed variables resolve against the base image
For a change unit of kind FIELD that is REMOVED, the system SHALL resolve its references against the
merge-base image, because a removed declaration has no position at head.

#### Scenario: Removed field with surviving readers
- **WHEN** a field is removed at head and a base-image index is available
- **THEN** the system resolves the readers that existed at base and reports each as a usage of the removed field

### Requirement: Declared read/write capability
A language plugin SHALL declare whether it can distinguish a field read from a field write, and the
system SHALL report the direction as unavailable for a language that does not declare it rather than
presenting an undirected access as a read.

#### Scenario: Plugin distinguishes direction
- **WHEN** the Java plugin declares READS_FIELD and WRITES_FIELD
- **THEN** each usage in the trace is labelled as a read, a write, or both

#### Scenario: Plugin does not distinguish direction
- **WHEN** a plugin declares only an undirected access edge type
- **THEN** usages are shown with the direction stated as unavailable for that language, and no usage is labelled a read by default

### Requirement: Partial reach is disclosed for generated accessors
The system SHALL declare a usage trace's reach as partial, and name the reason, when the changed field
belongs to a type whose accessors are generated by an annotation processor and those generated members
are not enumerated.

#### Scenario: Field read through a generated getter
- **WHEN** a field's reads occur through a Lombok-generated getter that is not enumerated as a member
- **THEN** the trace states that reach is partial because generated accessors are not enumerated, rather than presenting the resolved list as complete
